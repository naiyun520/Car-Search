# 性能检查与优化

检查日期：2026-09-23

## 结论

当前项目在本地生产形态数据量（用户 724、订单 857、支付记录 857）下，未发现阻止上线的纯性能问题。后端空闲资源占用、公开接口响应和小程序包体积均处于合理范围。此次采用有上限的线程池、短时配置缓存、数据库索引、响应压缩和小程序按需注入，不通过无限加线程、无限缓存或过度拆包换取表面性能。

真实微信登录、虚拟支付、退款、发货及供应商查询的耗时仍取决于正式密钥、微信后台权限、网络和第三方接口，必须在体验版和正式环境继续观察。

## 实测结果

- `GET /api/v1/bootstrap`：本机连续 25 次请求平均 34.86 ms，中位数 30.80 ms，P95 49.82 ms，最大 53.52 ms。
- 压缩：客户端声明支持压缩时，接口响应为 `Content-Encoding: gzip`。
- Java 进程：空闲工作集约 296.1 MB，私有内存约 338.5 MB，66 个线程；空闲 10 秒 CPU 时间增加约 0.047 秒。
- 小程序构建产物：72 个文件，约 226.7 KB；JavaScript 约 100.0 KB，图片和 SVG 约 78.9 KB。
- 自动测试：后端单元测试 14/14 通过，本地接口与安全契约测试 39/39 通过，小程序微信端构建通过。

以上数据来自 Windows 本地开发环境，仅用于发现明显回归，不能替代服务器压测。

## 已实施的服务端优化

1. 数据库连接池保持最大 10、最小空闲 2。对当前业务量足够，也避免低配服务器建立过多空闲连接。
2. Tomcat 请求线程最大 100、最小空闲 10、等待队列 100，均支持通过环境变量调整。
3. JSON、HTML、CSS、JavaScript 和 SVG 响应超过 1 KB 时启用 gzip。
4. 邮件通知使用独立线程池：核心 1、最大 2、队列 100，避免 SMTP 慢连接阻塞用户支付或查询接口。
5. 普通配置增加 30 秒进程内缓存，保存后立即刷新；用于访问控制的 `admin_path` 不缓存，保证旧后台地址立即失效。
6. `/api/v1/bootstrap` 将多次设置项查询合并为一次查询。
7. 新增订单状态/时间、安卓自动退款、用户订单、支付时间、退款时间及退款轮询索引。
8. 退款和支付轮询排序移除 `COALESCE` 函数，便于数据库利用索引。

## 已实施的小程序体验优化

1. 启用 `lazyCodeLoading: requiredComponents`，减少启动阶段无关组件加载。
2. 启动数据采用“网络请求与本地缓存并行”：缓存有效期 6 小时，网络成功后立即更新；网络异常时可先显示最近一次服务目录。
3. 存储启动数据改用异步接口，减少同步存储阻塞主线程。
4. 当前包体积很小，暂不强制分包。现阶段分包增加维护和页面跳转复杂度，收益有限。
5. 首页搜索直接在已加载服务中计算，输入搜索词时自动切回“全部”分类；分类使用横向滑动，避免分类较多时挤压或截断。
6. 首页四项能力展示和服务状态标签采用轻量 SVG/CSS，不引入图标字体或大型 UI 组件库。

## 上线建议与阈值

- 建议服务器至少 1 核 CPU、1 GB 内存；若同机运行 MySQL，建议 2 GB 及以上。
- Java 建议先设置 `-Xms256m -Xmx512m`。若同机内存不足，应优先分离数据库或提高内存，而不是继续压低堆上限。
- 保持 `DB_POOL_SIZE=10`、`TOMCAT_MAX_THREADS=100` 作为初始值。只有在慢请求并发确实排队、数据库仍有余量时再提高。
- 重点监控接口 P95/P99、5xx 比例、JVM 堆使用率、数据库活跃连接、慢查询、邮件队列、微信与供应商接口耗时。
- 建议告警线：接口 P95 连续 5 分钟超过 1 秒、5xx 超过 1%、JVM 堆持续超过 80%、数据库连接池持续使用超过 80%。
- 数据量增长到十万级订单前，应在生产规格的预发布环境使用脱敏数据执行并发压测，并根据慢查询日志复核索引，而不是预先堆叠大量索引。

## 未能在本地完成的验证

- 微信开发者工具中的首屏渲染耗时、真机弱网表现和 iOS/Android 虚拟支付链路。
- 微信支付、自动退款、发货通知和供应商接口的真实延迟及限流行为。
- CDN、反向代理、TLS、HTTP/2 及生产服务器带宽表现。
- 主密钥与线上密文未匹配前，无法完成真实供应商查询和微信敏感配置验证；这是配置可用性问题，不是性能问题。
